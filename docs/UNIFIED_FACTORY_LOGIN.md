# HyperFFactory – المصنع الموحّد الرسمي

## 1. تعريف مختصر

HyperFFactory هو المصنع الموحّد لتجميع وتشغيل الأنظمة التالية على السيرفر:

- SmartFriend Suite (هوية، ذاكرة، بوتات، Web/Gateway)
- FFactory / AI Stack (خدمات الذكاء الاصطناعي والدعم)
- سكربتات الفحص، الإصلاح، النسخ الاحتياطي، والتشغيل الآلي

> جميع الريبوهاِت على GitHub تستخدم للاستدلال والتوثيق فقط.  
> التشغيل الفعلي والاعتماد الإنتاجي على السيرفر داخل الهيكل الموحّد.

## 2. مواقع التنفيذ الرسمية

- المصنع الموحّد (Orchestrator):
  - `/root/HyperFFactory`

- أنظمة متكاملة تحت سيطرته:
  - `/opt/smartfriend-suite`  ← نظام SmartFriend Suite
  - `/opt/ffactory`          ← نظام FFactory / AI Stack (Stack مستقل متكامل)

أي تشغيل أو سكربت خارج هذه البنية يعتبر مخالفة لسياسة الهيكل الموحّد ويجب إصلاحه.

## 3. دور الريبوهاِت (للاستدلال فقط)

- `HyperFFactory`      ← التصميم والهوية للمصنع الموحّد.
- `hyper-factory`      ← مرجع لخط إنتاج بيانات بسيط (inbox → raw → processed → …).
- `ffactory` / `ffactory2` ← مراجع بنية الـ AI Stack (Postgres, Ollama, ASR, …).
- `smartfriend-suite`  ← كود SmartFriend المنتج (apps/gateway/bots/…).
- `smartfrind`         ← نسخة Legacy قديمة (غير معتمدة للإنتاج).
- `other`              ← سكربتات وأرشيف وتاريخ تجارب.

## 4. خريطة العمل الموحدة (Roadmap عالية المستوى)

### المرحلة 1 – التوحيد الأساسي

- توحيد مسارات التنفيذ تحت:
  - `/root/HyperFFactory`
  - `/opt/smartfriend-suite`
  - `/opt/ffactory` كنظام خارجي.
- تجميع سكربتات وتشخيصات الأنظمة داخل HyperFFactory/ imported / reports.
- إنشاء مركز صحّة موحّد (Unified Health Center).

### المرحلة 2 – الدمج والتكامل

- قناة تكامل رسمية بين HyperFFactory و SmartFriend (Health / Memory / Knowledge / Gateway).
- قناة تكامل رسمية بين HyperFFactory و FFactory (AI / ASR / Tools).
- توحيد مسارات النسخ الاحتياطي والسياسات التشغيلية.

### المرحلة 3 – التحسين والجودة

- تعريف مؤشرات أداء (KPIs) وتشغيل فحوصات دورية.
- لوحات تحكم موحّدة (CLI / Telegram / Web).
- تحسين الأداء، الأمان، والاختبارات المستمرة.

## 5. سياسة التشغيل

1) التنفيذ من داخل الهيكل الموحّد فقط.  
2) عدم المساس بمشروع FFactory المنتج (Stack مستقل، دمج فقط).  
3) عدم حذف أي قاعدة بيانات أو تقارير تشخيص أو أرشيف.  
4) GitHub للمرجع فقط، السيرفر هو مصدر الحقيقة الوحيد.

## 6. سياسة الهيكل الموحّد الصارمة (Unified Tree Strict Policy)

هذه السياسة مُلزِمة لكل سكربت/خدمة/نموذج يعمل على هذا السيرفر ضمن HyperFFactory:

1. **جذر المصنع الموحّد**:
   - الجذر الرسمي الوحيد للمصنع هو:
     - `/root/HyperFFactory`
   - وجود مجلد داخلي:
     - `/root/HyperFFactory/opt`
     جزء من الهيكل الموحّد وليس بديلًا عن `/opt` النظامية.

2. **ممنوع إنشاء ملفات خارج الهيكل الموحّد**:
   - يُمنع نهائيًا على أي سكربت أو خدمة تابعة لـ HyperFFactory أن تُنشئ:
     - ملفات
     - مجلدات
     - قواعد بيانات
     - Logs
   خارج الشجرة:
   - `/root/HyperFFactory/**`
   باستثناء عمليات قراءة/تكامل صريحة مع:
   - `/opt/smartfriend-suite`
   - `/opt/ffactory`
   التي تُعامل كنُظم متكاملة مستقلة (Integration فقط، بدون نسخ أو خلط ملفات).

3. **ممنوع استخدام symlink أو hardlink داخل الهيكل الموحّد**:
   - يُمنع نهائيًا إنشاء:
     - symlink
     - hardlink
   داخل `/root/HyperFFactory` لأي سبب، سواء إلى:
     - مسارات داخلية أخرى
     - أو مسارات خارجية (`/opt`, `/usr`, إلخ).
   - أي محاولة لإنشاء روابط تعتبر **مخالفة مباشرة** لسياسة المصنع الموحّد ويجب أن تُكتشف وتُصلَح.

4. **هدف أساسي: هيكل واحد كامل متكامل**:
   - HyperFFactory مبني على مبدأ:
     - «هيكل واحد كامل متكامل» Unified, Self-contained Tree
   - كل ما يخص المصنع (config, scripts, logs, reports, db, docs) يجب أن يعيش داخل:
     - `/root/HyperFFactory`
   - هذا يجعل:
     - النسخ الاحتياطي
     - الاستعادة
     - المراجعة
     - النقل إلى سيرفر جديد
     عملية خطية وواضحة.

5. **تثبيت المسارات والأسماء للأجيال القادمة من النماذج**:
   - جميع المسارات والأسماء المذكورة في هذا الملف تعتبر:
     - **Contract رسمي** بين:
       - البنية التحتية
       - والنماذج/السكربتات التي ستعمل لاحقًا.
   - أي نموذج أو سكربت جديد **ممنوع** أن:
     - يغيّر هذه المسارات.
     - يعرّف بدائل جديدة لها.
   - أي خطوة مستقبلية يجب أن:
     - تستخدم نفس المسارات/التسميات كما هي هنا.
     - توثّق أي إضافة جديدة في هذا الملف قبل استخدامها الإنتاجية.

6. **تقييد اللوحات والأنظمة المساعدة بالهيكل الموحّد**:
   - أي لوحة تحكم (Server Board / Web UI / Telegram Bot / CLI):
     - تقرأ حالتها وتهيئتها من داخل:
       - `/root/HyperFFactory`
       - وخصوصًا من:
         - `config/`
         - `docs/`
         - `reports/`
   - أي إعداد جديد للوحة السيرفر يجب أن:
     - يرجع إلى هذا الملف كمرجع للسياسة.
     - يذكر بوضوح أن HyperFFactory هو المصدر الوحيد للحقيقة.

7. **مصدر الحقيقة**:
   - هذا الملف:
     - `docs/UNIFIED_FACTORY_LOGIN.md`
   هو:
   - مرجع الهوية الرسمي للمصنع الموحّد.
   - المرجع الأساسي لسياسة الهيكل الموحّد.
   - يجب ربطه في لوحة الدخول (Server Login/MOTD) وفي أي لوحة إدارة مستقبلية.

8. **ضرورة تسجيل التقدّم والملفات والمسارات واقتراح الحالة الحالية في الخطة**:
   - كل عملية تشغيل/إصلاح/تهيئة ضمن HyperFFactory يجب أن:
     - تُسجّل في ملف Log واضح داخل:
       - `reports/` أو مسار لوج مخصص تحت `/root/HyperFFactory`.
     - توضّح بوضوح:
       - ما الذي تمّ تنفيذه؟
       - أي ملفات تم لمسها؟
       - ما هي المسارات المتأثرة داخل الهيكل الموحّد؟
     - تُحدّث الحالة التنفيذية في:
       - `plan_status.md` أو جداول meta تحت `db/meta/` (عند الحاجة).
     - تقترح صراحةً:
       - "الحالة الحالية في الخطة" (Current Plan State)
       - و"الخطوة التالية المقترحة" (Next Suggested Step)
       ليتم استهلاكها من:
       - لوحات السيرفر
       - والأنظمة الذكية (Workers / Orchestrators / Bots)
       كجزء من تدفق العمل الرسمي والتخطيط المستمر.


## 7. إلزام تسجيل التقدّم والمسارات والحالة في الخطة

1. **تسجيل التقدّم (Progress Logging Mandatory):**  
   - يجب على كل نموذج/خدمة/سكربت أن يكتب تقدّمه في:
     - ملفات تحت `reports/` (logs / JSON / summaries)
     - والسجلات تحت `db/meta/` عند الحاجة (مثل `hf_changes.db`).
   - أي خطوة تنفيذية مهمّة تتم بدون تسجيل تقدّمها تعتبر **مخالفة تشغيلية** لسياسة المصنع الموحّد.

2. **تسجيل المسارات (Path & Context Logging):**  
   - كل عملية إصلاح/فحص/تشغيل يجب أن تُسجّل مع:
     - اسم السكربت / الخدمة،
     - المسار الذي تعمل عليه داخل الهيكل،
     - وقت التنفيذ (timestamp)،
     - الحالة (نجاح / تحذير / فشل).
   - الهدف: تتبّع تاريخ التغييرات على الشجرة الموحدة بدون ضياع أي خطوة.

3. **ربط التقدّم بخريطة العمل (Plan-Aware Logging):**  
   - أي تغيير جوهري في الهيكل أو الخدمات يجب أن يُربط بـ:
     - بند واضح في وثائق الخطة (README/plan_status)،
     - وتحديث في `plan_status.md` يوضّح حالة التنفيذ (✅ / ⏭ / 🟡).
   - لا يُعتبر أي تغيّر "مكتمل" إلا إذا:
     - تم تنفيذه داخل الهيكل الموحّد،
     - وتم تسجيله في التقارير،
     - وتم عكسه في حالة الخطة.


## إلزام تسجيل التقدّم (Progress Logging Mandatory)

ضمن سياسة HyperFFactory الموحّدة، يُعتبَر تسجيل التقدّم جزءًا أساسيًا من تشغيل المصنع:

- كل سكربت/خدمة/عامل يعمل تحت `/root/HyperFFactory` يجب أن:
  - يكتب مخرجاته وتقاريره في مجلد `reports/` داخل الجذر.
  - يستخدم عند الحاجة قواعد بيانات الميتا في `db/meta/` (مثل `hf_changes.db`) لتسجيل التغييرات البنيوية.
- أي خطوة تنفيذية مهمّة (فحص / إصلاح / تشغيل / تكامل) تتم بدون تسجيل تقدّمها:
  - تُصنَّف "مخالفة تشغيلية" ويجب إصلاحها في أقرب دورة حوكمة.
- يجب ربط التقدّم بخريطة العمل عبر:
  - تحديث حالة البنود في `plan_status.md` باستخدام الرموز (✅ / 🟡 / ⏭).
  - الحفاظ على `README.md` و `plan_status.md` كمرجعين رسميين لحالة التنفيذ.
